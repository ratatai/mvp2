## 6. Исследование для миграции приведения схемы

Файл: `supabase/migrations/20260929144644_reconcile_august_schema_to_canonical.sql`.

**[Ф]** На 2026-10-06 файл присутствует в рабочем каталоге как
**неотслеживаемый** (`??` в `git status`) и в этот коммит документации
**не включён** — по прямому указанию.

### 6.1 Метод

**[П]** Ожидания строились не от руки, а запросами к базе, созданной из
настоящих `001_initial_schema.sql` и `002_security_hardening.sql`. Использованная
интроспекция каталога PostgreSQL: `pg_policy` + `pg_get_expr`,
`pg_get_constraintdef`, `pg_get_indexdef`, `pg_get_functiondef` / `prosrc` /
`proconfig` / `prosecdef`, `pg_get_triggerdef`, `pg_depend`, `pg_rewrite`
(`_RETURN`, `ev_type`), `pg_default_acl`, `query_to_xml` для разрешения имён во
время выполнения.

### 6.2 Принятые свойства миграции

**[П]** Описано по итогам ревью; проверяется чтением самого файла.

- Атомарность по построению: вся миграция — один оператор
  `DO $reconcile$ … $reconcile$`; временная таблица снимка `profiles` —
  `ON COMMIT DROP`.
- Блокировки (`ACCESS EXCLUSIVE`, `SHARE`) берутся **до** подсчётов.
- Никакого `DROP ... CASCADE`: политики удаляются по именам, таблицы — в порядке FK.
- Любое отклонение даёт **BLOCKED**, а не автоисправление.
- Сверка `auth.users` целиком по md5 до и после.

### 6.3 Подтверждённые дефекты, найденные и исправленные в ходе работы

**[П]** Перечень из переписки; каждый пункт проверяется по тексту миграции.

| Дефект | Как исправлен |
|---|---|
| `btrim()` снимает только пробелы, не переводы строк | нормализация `btrim(regexp_replace(x,'\s+',' ','g'))` |
| `%L` печатает boolean как `t`/`f`, тогда как фактическая сторона сравнения использовала `::text` | литералы приведены к фактическому виду |
| `raise exception '…%%s', a, b` → «too many parameters» | оба аргумента свёрнуты в один `format()` |
| `DROP TABLE listings` падал: политика `profiles_select_active_seller` читает `listings` | сначала удаление всех политик по именам, затем таблицы в порядке FK |
| Постпроверка блокировала сама себя: встроенные определения функций не совпадали с комментариями из 001 | все четыре определения заменены дословным текстом из 001 |
| Классификация политик по строковым литералам: три политики определялись неверно | сравнение полного определения с зафиксированной выгрузкой |
| Маркер требовал отсутствия `listings.specs`, тогда как в реальной августовской схеме колонка есть — миграция не запустилась бы никогда | исправлено по реальному бэкапу |
| `regexp_replace(prosrc, '\s+', ' ', 'g')` скрывал изменение семантики комментариев `--` | дословное сравнение `prosrc` с нормализацией только CRLF/LF; дополнительно сверяются язык, сигнатура и возвращаемый тип |

### 6.4 Находка по правам на `listing_sellers`

**[П]** В Supabase default-привилегии дают `anon` и `authenticated` полный набор
прав на объекты в `public`, включая view `listing_sellers`. Зафиксировано с
точной ACL; проверка не ослаблялась.

**[П]** Решение владельца (вариант 1): требование `SELECT` для `anon` и
`authenticated` оставлено; требование отсутствия `INSERT/UPDATE/DELETE` в ACL
снято в пользу проверки фактической невозможности записи; дословная сверка
определения, колонок и `reloptions` сохранена; добавлен BLOCKED при
пользовательских триггерах на view и при лишних rewrite-правилах помимо
штатного `_RETURN`. Найденные объекты не удаляются автоматически.

### 6.5 Как это проверялось

**[П]** Все пункты ниже — из переписки, журналов в репозитории нет.

- Одноразовый PostgreSQL 16.13 — прогон каждого guard'а.
- Отдельный одноразовый локальный Supabase: свой `project_id`, свои порты,
  контейнеры и volumes; изоляция проверялась до запуска; remote link, токены и
  production-данные не копировались.
- Дайджесты `pg_dump` для сравнения состояний.
- На изолированном настоящем Supabase показан атомарный откат: после откатa
  `pg_dump` побайтово совпал со свежесозданной legacy-схемой.

**[З]** Перенести эти прогоны в воспроизводимый скрипт или журнал в
репозитории, чтобы они перестали быть сведением «из переписки».

## 8. Нерешённые вопросы исследования

1. **[Ф] Сравнение готовых open-source маркетплейс-платформ не проводилось.**
   Выбор «писать на Next.js + Supabase» зафиксирован как решение, но
   исследования альтернатив (Sharetribe, Medusa, Saleor, Vendure, готовые модули
   классифайдов) с внешними источниками нет. Если обоснование нужно для открытой
   публикации — его предстоит сделать. **[З]**
2. **[Ф] Нет внешних источников по рынку.** Объём спроса, конкуренты, каналы не
   исследовались. Отдельные документы владельца на эту тему существуют локально,
   но в эту работу не входили и в выводы не включены.
3. **[П] Бренд взят из локальной копии сайта** из-за 403 на `ratatai.com`;
   актуальность не перепроверена.
4. **[П] `avif_autodetection` у bucket `listing-images` неизвестен** — в выгрузке
   параметра не было, значение не предполагалось.
5. **[Ф] Производительность не исследовалась:** нет замеров планов запросов при
   JSONB-фильтрах по `specs` на объёмах больше тестовых, нет Lighthouse или
   бюджетов.
6. **[Ф] Доступность не проверялась инструментально.** Ловушки фокуса и цели
   44 px покрыты Playwright'ом, но axe/WAVE-аудита, проверки контраста по всей
   палитре и прогона со скринридером не было.
7. **[Ф] Юридические тексты** написаны под эту систему, но юристом не
   проверялись.
